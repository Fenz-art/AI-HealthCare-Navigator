Backend Gaps That Block the Frontend
No GET /sessions/:id — Command Center cannot load session state
No severity-based orchestration — Client must manually pass activeIngredient and providerType; the backend doesn't derive pharmacy vs clinic from severity
No medication extraction from symptoms — Spec's extractor.ts doesn't exist
No translation — Interpreter is English-only text assembly; no Gemini translation to local language
No CORS — Direct browser → Express calls will fail
No request validation on POST /sessions (no Zod schema)
Spec vs Reality: The Navigation Flow
Your intended flow:

Symptoms → Severity → Medication Extraction → Local Meds → Provider Discovery → Interpreter → Outcome
What actually runs today on POST /sessions:

Symptoms → Gemini Severity
         → Meds (only if client sends activeIngredient + countryCode)
         → Providers (only if client sends lat/lng + providerType)
         → English interpreter text
The "brain" that connects severity → provider type → ingredient extraction is not wired. The frontend would need to duplicate that logic unless the backend orchestrator is built first.

Bottom Line
You have a functional backend MVP for healthcare navigation — the database schema, AI severity routing, medication equivalence lookup, Geoapify provider search, interpreter context, and outcome recording all exist and work as Express endpoints.

What you do not have is any of the product surface: no UI, no design system, no motion, no maps in the browser, no storytelling components, and no way for a traveler to actually use CareCompass. The entire frontend vision — including the 7 narrative motion components, Command Center, and calm/trustworthy visual language — is specification only.

The backend also needs orchestration glue before the frontend can deliver the "one next step" experience without the client guessing providerType and activeIngredient.
